# `vvv` — Canonical Shim

## Purpose

Force a **pause-and-clarify** ritual before any code is written. The agent
proposes 5 understanding questions; the human answers (or skips). Output is
a written-down baseline that `nnn` will plan against and `gogogo` will
execute against.

`vvv` is the gate that stops "agent ran ahead and built the wrong thing."

## Pre-flight (adapter contract) — added 2026-05-11

> **Adapters MUST refuse `vvv` when no Trinity session is active.**

`vvv` writes to `THINK/01_PROMPT.md` of the active session. With no
session, there is nowhere to write — the kernel will refuse, but the
adapter must refuse *first* with a clear pointer to `sss` so the
operator does not see a cryptic kernel error.

### Required adapter check

Before invoking `ai vvv`, the adapter MUST:

1. Read `.ai/state/status.json` (or run `ai lll`) to determine whether
   an active session exists.
2. If **no active session**: refuse `vvv` with this exact intent
   (paraphrasing in the operator's language is fine):

   > No active Trinity session. Run `sss <task-slug>` first to open
   > one, then re-run `vvv`. Trinity workflow:
   > `lll → sss → vvv → nnn → gogogo → rrr`.

3. If **a session exists but graph_state is not `THINK`**: refuse with
   a pointer to the relevant next ritual (`nnn` if at SANDBOX, `gogogo`
   if at DO, `rrr` if at VERIFIED, etc.). Re-running `vvv` mid-flight
   is a Trinity boundary violation and the kernel will reject it.
4. If both checks pass: proceed to render the 5 questions per
   `## What the kernel does` below.

### Why this lives in the shim, not the kernel

The kernel currently refuses ritual chains without a session at the
audit-chain level (`lll` snapshot shows "no active session — `ai
session new <task>`" and `ai rrr` returns "No active session. Cannot
run rrr."). However:

- Different kernel rituals refuse with slightly different error shapes
- An operator hitting an adapter slash command (`/vvv` in Claude Code,
  `vvv:` in Cursor) should not have to read a Python traceback
- Adapter-level refusal lets us surface `sss` as the literal next
  command in the operator's own UI

When the kernel grows a uniform `session_required` precondition gate
(roadmap), this adapter-level check becomes belt-and-suspenders rather
than primary enforcement.

### Anti-pattern explicitly forbidden

- ❌ Adapter sees no active session and silently calls
  `ai session new <auto-generated-slug>` before firing `vvv`.

  Hiding the session boundary erases the operator's chance to choose
  a meaningful slug, breaks audit traceability ("who decided to open
  this session and why?"), and turns `sss` into an invisible step
  the operator never owns. Always require the operator to fire `sss`
  themselves with a real slug.

## CLI invocation modes (`--show` vs submission) — added 2026-06-12

The kernel CLI has two distinct modes; adapters MUST use them in a
**two-phase** flow:

| Mode | Command | Exit | Side effects |
|------|---------|------|--------------|
| **Prompt** (phase 1) | `ai vvv --show` | 0 | none — no writes, no audit event |
| **Submission** (phase 2) | `ai vvv --answer N=... ×5` or `--answers-file <path>` | 0 on pass | writes `THINK/01_PROMPT.md` + `.state/vvv_pass`, appends audit events |

**Bare `ai vvv` (no answers) is NOT a prompt mode.** The kernel treats
it as a failed submission per Article IX (evidence trail for failed
proposals): it prints the questions, exits 2, **and appends a
`vvv.failed` (reason: missing_answers) event to the audit chain**.
Adapters that invoke bare `ai vvv` to "display the questions" pollute
the audit trail with false failures — always use `--show` for phase 1.

The human answers (or explicitly approves an AI-drafted answer set —
show-before-submit) between the two phases.

## When to invoke

- After `sss:` before any plan or code
- Whenever scope, acceptance, or constraints feel ambiguous mid-session
- **Always** before destructive or wide-reaching operations
- Skipping `vvv` is a Trinity **D2** boundary violation — the kernel
  refuses to transition `THINK → SANDBOX` without `vvv_pass`

| Field | Required | Source |
|-------|----------|--------|
| task description | yes | session metadata (set by `sss:`) |

## What the kernel does

1. Loads the active session's `THINK/00_CONTEXT.md` (or empty)
2. Generates **5 understanding questions** covering:
   - Goal — what success looks like
   - Scope — what's in/out
   - Constraints — what can't be touched (policies, boundaries)
   - Acceptance — measurable signal of "done"
   - Risk — most likely failure mode
3. Waits for human answers (or explicit "skip" with reasons)
4. On answer, writes `THINK/01_PROMPT.md` and a `vvv_pass` marker
5. Records `vvv.proposed` and `vvv.passed` events to audit chain

The **files-expected list is the agent's duty, not the kernel's** (the
kernel has no independent source for it): the agent's drafted Q2 (Scope)
answer MUST embed the concrete file paths it expects to touch. Aligned
2026-06-12 — earlier revisions promised kernel-written sections that
never existed in `01_PROMPT.md`.

## Behavior contract

**MUST**
- Produce exactly 5 questions (not 3, not 7) — 5 is the contract
- Block the `THINK → SANDBOX` transition until `vvv_pass` exists
- Quote any constraint from `.ai/policies/` verbatim if relevant
- List concrete files (paths) the agent expects to touch — embedded in
  the Q2 (Scope) answer, since the kernel writes no separate section
- Append `vvv.proposed` and (on pass) `vvv.passed` to audit

**MUST NOT**
- Skip itself ("task is simple") — Decision D2 violation
- Generate code in the same response
- Mutate any file outside `THINK/`
- Decide `vvv_pass` autonomously (only human or verifier rule sets it)
- Use bare `ai vvv` as a question prompt (use `--show`)

## Output shape

```
THINK/01_PROMPT.md
├── # `vvv` — 5 Questions
├── ## Q1 — Goal
├── ## Q2 — Scope        (MUST embed the files-expected list)
├── ## Q3 — Constraint   (quote relevant .ai/policies/ verbatim)
├── ## Q4 — Acceptance   (measurable / executable signal)
└── ## Q5 — Risk
```

(Each section holds the question + the approved answer. There are no
separate kernel-written "Files expected / Acceptance criteria /
Constraints" sections — that content lives inside Q2/Q4/Q3
respectively; aligned to the actual kernel output 2026-06-12.)

## Adapter rendering hints

Adapters should:
- Display all 5 questions at once (don't drip one-by-one)
- Show "files expected" list for human spot-check
- Make answers easy: numbered prompts, default-on options where sensible
- After human responds, render the `vvv_pass` marker visibly

## Anti-patterns

- ❌ Agent writes code in the same response as the questions (skip)
- ❌ Adapter wraps `vvv` with an LLM judge that auto-approves easy tasks
- ❌ Adapter omits a question because "it's obvious" — kernel verifier
  checks for 5
- ❌ Adapter invokes bare `ai vvv` as prompt mode — exits 2 and appends
  a false `vvv.failed` to the audit chain (use `--show`)
